# Design: pipeline-review-hardening

## Context

见 proposal.md — Why。这里只记录实现层面的约束与取舍。

现有解析器 `lib/tasks.mjs` 用逐行状态机解析 `tasks.md`：`inComment` 布尔量表示"当前行处于跨行 HTML 注释内"，遇到含 `<!--` 的行整行 `continue`。消费方有四个入口共用 parser：`reconcile.mjs`、`merge-task.mjs`、`contract-check.mjs`、`freeze-check.mjs`，加 `hotfix.sh`。任何解析语义变化都会同时影响这五个门禁——这是"单一属主"设计的收益，也是本次必须为每个改动补回归用例的原因。

`contract-check.mjs` 的场景对账是 change 级的，但测试语料是 skill 级的。这个口径错配是 `--final` 恒红的结构性原因，不是测试写得不好。

`freeze-check.mjs` 判断的是"这份计划现在能不能开工"，但它对任何路径都跑同一套规则，包括 `openspec/changes/archive/` 下的历史记录。

## Goals / Non-Goals

**Goals**

- 行内注释不再改变任务集合与字段归属。
- `Verify with` 只做 Markdown 解包，不改写 shell 结构。
- 收尾对账在"change delta + skill 级测试语料"这个真实组合下可给出有意义的结论。
- 冻结预检对含 MODIFIED 的 change 可给出结论（继承来的场景不算本 change 的义务）。
- 归档 change 的只读诊断不产生阻断判定。
- shell 用例表承载的场景参与静态对账，不被静默跳过。
- 门禁模块对外只暴露真正被消费的符号。

**Non-Goals**

- **不清理 31 条 phantom 存量债（收尾口径；整树 + 整个 test/ 目录口径为 83 条）**。测试标题引用了 spec 从未写过的编号，本 change 只提供可执行的预算口径，清偿是独立工作。
- 不改 `merge-task` 的 exit 码语义、Pod 闭包、Done 行语法、证据闸门字段集、角色路由。
- 不引入基于 AST 的 Markdown 解析器。现有逐行状态机在"只剥注释区间"这个语义下是充分的，换解析器会把改动面扩大到全部五个门禁。

## Decisions

### D1 注释：剥区间，而不是丢弃整行

旧实现在看到 `<!--` 或 `-->` 时 `continue`，理由写在注释里是"注释里的 `- Foo: bar` 不该参与解析"。这个理由成立，但手段过宽：它对**整行**生效，于是 `- [ ] 1.2 T-02 b <!-- 待定 -->` 连任务声明一起丢掉。

新实现分三步：若处于注释态，找到 `-->` 的位置，丢弃它之前的部分并退出注释态；然后在剩余文本里循环剥离每个 `<!-- ... -->` 区间；只有开头没有结尾时，保留注释前的内容并把状态置为注释中。整行剥完若为空白则跳过。

**为什么不是"先用正则删掉所有注释再解析"**：跨行注释要求"开标记之前的内容保留、闭标记之后的内容保留"，用 `[\s\S]*?` 非贪婪匹配整段会连带吞掉中间真正的任务行——那正是要修的缺陷的镜像版本。状态机逐行推进才能保住两侧。

**替代方案**：让写作者不许用行内注释（改校验拒绝）。否决——模板与真实 `tasks.md` 已经大量使用注释写字段规则，拒绝等于让既有文件全部变红，而缺陷在解析器一侧。

### D2 剥包裹只认引号，不认括号

`stripWrappingQuote` 原本剥六对定界符。实测 `("a" || "b")` → `"a" || "b"`（无害），但 `(cd sub && make)` → `cd sub && make`（子 shell 语义消失，`cd` 污染后续命令的 cwd），`[ -f x ]` → 命令无法执行。剥括号是"看起来像 Markdown 包裹"的误判：方括号与花括号在 shell 里是测试表达式与命令组，不是排版符号。

新实现只保留反引号、双引号、单引号三对，并且仍要求"内部不含未配对的同种定界符"——`\`a\` && \`b\`` 有三个反引号，不是一对包裹，原样保留。这是既有 `containsUnbalanced` 判据的既有行为，本次不改。

**替代方案**：白名单"只剥反引号"。否决——`Verify with: "node --test x.mjs"` 是真实使用形态（YAML 味道的写法），并且已有测试固定了它。

### D3 收尾对账：`--baseline` 并入声明、`--max-phantom` 记预算

用 change delta 跑 skill 级测试语料，缺的永远是"别的 change 的场景"。实测（2026-10-27，本仓）：

| 口径 | phantom | untested | rc |
| --- | --- | --- | --- |
| 只传 delta | 38 | 3 | 1 |
| delta + `--baseline openspec/specs` | 31 | 0 | 0（配 `--max-phantom 31`） |
| 只传整树 `openspec/specs` | 42 | 51 | 1 |
| 整树 + 整个 `test/` 目录 | 83 | 14 | 1 |

第四行比本 change 动手前高 5 条（78→83），来源是新纳入语料的 `contract-check.test.sh`：它自己带着 `# SCEN-CON-19/20/21/24` 四条标注，加上夹具里一条 `SCEN-SH-01`——都是本 change 新增编号，在整树口径下尚未进基线。这是口径本身的已知特性，不是新增债务。

两个开关各自解决一半：
- `--baseline <spec 目录>` 做**两件事**：把基线已声明的编号并入 phantom 判定（38→31），并把基线场景从 untested 判定里排除（51→0）。两者缺一不可——第一版只做了前者，收尾仍然 rc=1，因为 delta 为满足 MODIFIED 的整块替换语义必须原样抄回 11 条基线场景，抄回来后它们被当成本 change 未覆盖的义务。
- `--max-phantom <n>` 默认 0，即默认行为与旧版一致。收尾时贴当轮实测数，新增一条越界失败。

**为什么不是"把 spec 传整树"就够**：不够。整树口径下，基线里那些确实没有测试引用的场景会全算 untested（实测 51 条），把本 change 拖红。这不是本 change 的债。

**为什么不清零 31 条**：那需要给每个测试标题重新编号或补写 31 个 spec 场景，工作量与风险都不属于"修门禁"。把它记成预算，等于把存量债从"隐性恒红"变成"显式可见"。

### D3b shell 用例表的场景通道

`contract-check.test.sh` 用 `# SCEN-…` 注释标注每条用例在验什么，但扫描器只认 JS 扩展名，这些场景永远不可见——本 change 的三条场景（CON-19/20/21）由 shell 用例承载，收尾时被判"无测试引用"。

修法：`.sh` 只进**场景通道**，不进消息通道（shell 里没有 `assert.throws`）。两个细节是实测踩出来的：
- **必须剥 heredoc 夹具**。`cat > x.md <<'EOF'` 里写着 `#### Scenario: SCEN-BASE-01`，那是以 `#` 开头的行但属于被构造的输入。不剥会把夹具编号算成 phantom（实测 31→41）。
- **场景通道不能走 `stripComments`**。JS 测试全部把场景编号写在 `// SCEN-…` 行注释里，剥注释会把它们全删掉，每个场景变成 untested（实测：加 stripComments 后 shell 套件一次转红 10 条）。场景编号在注释里是标注、在断言里是引用，两者都算数。

`Write scope` 退回找测试文件时同步收窄到 `VERIFY_FILE`（`*.test.mjs` / `*.test.sh`）：scope 里实现与测试混写，按扩展名过滤会把 `contract-check.mjs` 也当成语料（实测产生 2 条 undeclared 误报）。scope 里一个测试形状的文件都没有时退回全量，保持旧行为。

### D4 `typeof` 右侧不出现在消息通道

`assert.equal(typeof error.message, 'string')` 命中了 `.message\s*(?:,|===?)\s*STR`。修正方式是提取断言消息前先把 `typeof <expr>` 整体替换成 `typeof`，而不是给 `tested` 加更多过滤——过滤是在错误的位置补洞，替换是去掉误报的源头。

### D5 归档路径只诊断

判定条件是路径里含 `archive` 段。归档 change 的 `blocking` 数组全部转为 advisory 并加前缀 `[已归档，仅记录]`，退出码 0，输出明确写"历史记录只读诊断，不做可冻结判定"。

**为什么不是"归档不跑这个命令"**：诊断历史 change 是有价值的（复盘"当时的计划有没有缺陷"）。问题不是跑，是把判定当阻断。

**为什么不按"归档时间 vs 规则引入时间"精确判断**：那需要把规则版本写进 schema 并在每次归档时快照，成本远高于收益。粗粒度（整个 archive 目录不阻断）已经消除"永远红着"这个具体危害。

### D6 schema 副本一致性用逐字节断言

`openspec-schema/` 是源头，`openspec/schemas/paseo-pipeline/` 是 `cp -R` 安装产物，此前零守护。测试遍历两侧文件列表并逐字节比较，缺失任一侧也失败。先红后绿已验证（改动安装副本的 `schema.yaml` → 红；还原 → 绿）。

**替代方案**：把安装副本做成符号链接。否决——`openspec init` 的目标仓库需要真实文件；而且 Windows 上符号链接不可靠。

### D7 report 不输出恒定占位字段

删掉 `firstPassUnknown` / `readyWaitUnknown`，改为末尾一行文字说明"本报告不覆盖什么"。理由：一条永远是同一个值的字段不传递信息，只会让报告看起来覆盖了它。`--json` 消费方若依赖这两个键会拿到 `undefined`——这是有意的破坏性变更，已在 proposal 标注。

### D8 死导出内部化

`SMOKE_TIMELINE_FIELDS`、`requiredFields`、`CONTRACT_FIELDS` 模块外零引用。前两个改为模块内常量/函数（保留注释说明为什么独立列出），`CONTRACT_FIELDS` 改为非导出常量，唯一读者 `isContractField` 仍是导出。**不删代码**——它们是判据的可读性来源，删掉会让注释失去指代对象。

## Risks / Trade-offs

- **[行内注释剥离误伤正文]** 若某条任务标题里合法地含有 `<!--`（如文档在讲 HTML），会被剥掉。→ 缓解：`<!--` 在任务标题里出现本就极罕见；且旧行为是整行丢弃，新行为只会丢注释区间，严格更宽松。
- **[`--max-phantom` 被当成豁免]** 调用者可能填一个大数让门禁永远绿。→ 缓解：SKILL 写明"预算数字必须是实测过、且该条在此前 change 里已存在的"；这是文档约束，不是代码约束——但这条约束的效力与"人是否诚实"无关，而与"报告里能不能指出这个数字从哪来"有关。
- **[归档豁免掩盖真实缺陷]** 归档 change 里的问题不再阻断，可能被忽略。→ 缓解：仍以 HINT 逐条打印；且归档 change 已经合入主干，阻断它不改变任何已发生的事实。
- **[D7 的破坏性变更]** 依赖 `--json` 那两个键的脚本会拿到 `undefined`。→ 缓解：模块外零引用已实测（`grep` 无匹配）；唯一消费者是测试，本次一并更新。
- **[测试语料的场景编号是历史债]** 新增用例继续在标题里写 `SCEN-CON-*`，可能继续推高 phantom。→ 缓解：本次新增用例使用 `SCEN-CON-15` 至 `SCEN-CON-25`，且**每个编号都已写进本 change 的 spec delta**，因此收尾口径下不产生新的 phantom；合入后随 delta 归档进入主 spec。夹具里构造 spec 形状文本时复用已有编号（`SCEN-DMO-77`/`-99`）而不是新编，避免只存在于夹具里的编号长久留在 budget 里。
- **[`.sh` 进场景通道带来夹具噪声]** shell 用例表里的 heredoc 夹具含 `#### Scenario: SCEN-…`，整文件扫会把它们算成 phantom（实测 31→41）。→ 缓解：`shellScenarioSrc` 先按 heredoc 界限剥整段，再只留 `#` 行；实测剥后 phantom 回到 31。
- **[`--baseline` 削弱 untested 判定]** 调用者可以把整树当基线，绕过新增场景的测试义务。→ 缓解：只排除**基线已声明**的编号；本 change 自己新增的场景不在基线里，仍判 untested（实测：新增 9 条全部要求被引用）。忘了传 `--baseline` 时门禁变严而非变松。
- **[`VERIFY_FILE` 收窄可能漏掉非常规测试文件名]** 若某测试文件不叫 `*.test.*`，退回 scope 时不会被认出。→ 缓解：scope 里一个测试形状的文件都没有时退回全量，保持旧行为；只在该判断有信息可用时才收窄。
