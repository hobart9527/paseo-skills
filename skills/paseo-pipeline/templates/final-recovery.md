Only DEVIATION (cites a SCEN, acceptance row or named standard plus a counterexample) enters a code-fix task; CONTRACT_GAP and REQUIREMENT_GAP never enter that loop and are never relabeled DEVIATION. A CONTRACT_GAP/REQUIREMENT_GAP with a realistic wrong outcome needs human disposition before CP-2/merge: amend the contract by delta R0 + CP-1, or explicitly accept the risk. ENHANCEMENT goes to non-blocking backlog. Do not merge an ad-hoc fix or reopen a Done task.
   **Batch.** One round's DEVIATIONs become one amendment and one repair wave: a new task per coherent fix, split by domain into parallel tasks where Write scopes allow. Record the finding, SCEN, narrow Write scope, dependencies and executable Verify; retain existing Done evidence. **A repair task normally overlaps a Done task's Write scope, so it must name that task in `Depends on`** — `freeze-check --structural` rejects an overlapping pair with `SCOPE_CONFLICT` when neither depends on the other. Repairs depend on each other only when their own scopes overlap; do not chain them serially. The author commits the contract-only amendment on integration; run `freeze-check.mjs <change-dir> --structural`; a new interface/security boundary needs delta-only amendment R0 against its parent SHA (one round). Obtain human CP-1 approval of the amendment before dispatch, unless covered by a pre-authorization (below); if the contract changes after approval, obtain approval again. Every approval binds to a SHA in `run-log.md`; an "approach only" approval is not one. The existing pipeline continues even if this small repair alone would not qualify as a new Tier 3 pipeline.
   **Pre-authorized budget.** The human's verbatim CP-1 approval of "up to 1 FINAL repair wave of ≤N tasks, DEVIATION only" is recorded in `run-log.md`. It covers exactly one amendment that is DEVIATION-only, has ≤N tasks and adds no new interface or security boundary (so no amendment R0). The main session then appends `Approval: pre-authorized repair wave (<cp1-approval-timestamp>) applied to <amendment-sha>` to `run-log.md`; without that line naming the amendment SHA, dispatch is not authorized. Anything outside this envelope, or any CONTRACT_GAP, needs fresh human CP-1 for its SHA.
4. Create `task/<change>/<new-T-id>` from the approved amended integration tip; install the hook and dependencies. Dispatch `gaogong` with `templates/worker.md`. Run `pipeline-run.mjs merge <change-dir> <new-T-id>` in integration. The normal scope, provenance, frozen Verify, regression and Done gates apply unchanged. Never cherry-pick around them.
5. Once all tasks are Done and integration is clean, capture `git rev-parse HEAD` as the new final SHA. Rerun the full suite and every `Required=yes` acceptance command at that exact SHA, and have the FINAL reviewer run round 2 at the same SHA: delta only (fix diff, affected behavior, open ledger items). Use one `anchasi` session for all FINAL rounds of a change. A replacement (same profile, never the implementer's model) reads the ledger first, inherits the round budget, and the reason for replacement is recorded with its agent id. Record commands, results, reviewer identity, verdict and full SHA; no pass carries over to a new SHA.
   **Bound: at most 2 FINAL rounds per change** (round 1 full, round 2 delta), plus one reopen delta round only if (b) is chosen. After round 2 with any NOT_MET or UNVERIFIABLE row, the human must choose one: (a) accept residual risk — `FINAL: human-accept(@<sha>)` in `review.md`, open items and reason in `rulings.md`, `Approval: FINAL residual risk accepted for <sha> — <reason>` in `run-log.md` (mirrors R0; never written as a reviewer pass; checked by the human at CP-2); (b) reopen at contract level — delta R0 + CP-1, then exactly one repair wave and one reopen delta round (the only round beyond the two); (c) terminate the change. (b) can be chosen at most once per change; if any NOT_MET or UNVERIFIABLE row remains after the reopen delta round, only (a) or (c) remain. There is no fourth default: no unbounded repeat, no silent stall. Before round 2 the main session may supply missing evidence for an UNVERIFIABLE row (environment fix, acceptance run); that is not a repair task.
6. Evidence binds to the reviewed code SHA. **Sequence:** while integration HEAD equals the reviewed SHA and before any record commit, run `acceptance check` (it requires `sourceSha` = HEAD, `acceptance-run.mjs:90-102`) and log its command, exit status and the reviewed SHA in `run-log.md`. Only then make record commits, touching nothing but `openspec/changes/<change>/{review.md,rulings.md,run-log.md}` (ledger, `FINAL: human-accept`, rulings, approvals). Immediately before CP-2, verify `git diff --name-only <reviewed-sha>..HEAD` lists only those files, and that the logged check is bound to the reviewed SHA; do not re-run `acceptance check` at the record HEAD, where it is expected to fail. Any other path invalidates the evidence: redo it at the new SHA as a delta review of what changed. A change that only updates the record file's SHA is not a new review round; any substantive implementation or contract change counts against the original FINAL budget. This SHA-only rule is not a loophole for substantive changes. Also verify the worktree is clean, main has not moved since review, all commands passed, and no NOT_MET or UNVERIFIABLE row is unaccepted. Report evidence and task SHAs; CP-2 stays human.

## Interrupted merge marker after Done

If `plan` shows the task Done but a pending ref remains after a crash, inspect the clean integration worktree, first-parent merge commit, Done source, and task tip. A verified completed merge needs no retry; leave the stale ref as evidence. Never clear it to bypass a gate. A dirty worktree is not proof of committed Done; reconcile it first.
