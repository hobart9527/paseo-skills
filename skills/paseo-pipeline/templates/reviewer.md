# Independent Reviewer Brief

Mode: `R0 | FINAL`. Change: `<id>`. Evidence: `<paths / base / tip>`.

Read-only: do not edit files, create commits, or change workspace state. You run in a separate workspace; the provider cannot enforce read-only, so this rule is yours to keep. Any write voids your verdict. Use only the stated contract and evidence. Findings must include `path:line` or reproducible reasoning. No broad refactor requests.

## R0 — frozen-change review

Optional read-only aid: `node "$PIPELINE_HOME"/r0-hotspots.mjs openspec/changes/<name>` lists declared task Uses, interfaces, risk surfaces and Verify plus MODIFIED/REMOVED requirement headings from the local worktree draft, not a commit-bound source. It never executes Verify. It uses the tasks parser and only recognizes standard spec headings; missing declarations, other formats, call sites and semantic effects are not discovered. Parse errors and missing/unreadable specs require attention. This is not validation or a substitute for independent R0 or CP-1.
Review Proposal, Specs, Design (when present), Tasks, Acceptance as one package, before CP-1. Check factual claims against source (`path:line`), assumptions, SCEN observability, scenario/task coverage, vertical slicing, scope conflicts, real frontier concurrency, and Verify feasibility. Prioritize substantive counterexamples: user intent, missing observable behavior, cross-task interface semantics, and realistic ways each Verify could pass while its claimed behavior is wrong. Assess risk against the actual change, not labels alone. Source-text assertions can establish textual properties but cannot prove runtime behavior, even for `Review: mechanical`. Flag unsupported behavioral claims as contract defects. Classify every finding as `BLOCKER` (contract would produce a wrong or unverifiable task) or `NIT` (wording, numbering, or a non-blocking improvement); only blockers prevent CP-1, and the main session records accepted NITs in `rulings.md`.

**Shared boundaries and risk coverage come first — they are where blockers live.** Walk every surface two tasks share: interface carriers (skeleton/`Interface:`/`Uses`), data semantics (identity, idempotency, invalidation), error codes, audit sinks, rollback paths. Each must be stated in a scenario THEN (and a design decision when the carrier is a choice) so a worker can implement from it; an undefined or ambiguous shared surface is a BLOCKER with a counterexample. Then run the author's risk checklist yourself — data migration/persistence schema; credentials/security/audit; cross-task identity or idempotency; external protocol/vendor; destructive/rollback — and check every tripped axis is frozen by a scenario that would fail if the semantics were wrong. An axis the author left unfrozen is a BLOCKER even if no task currently contradicts it. A worker who would need to survey the repository to start means the packet is incomplete.

**Review the whole package in one pass, not finding by finding.** Report every blocker your evidence supports in this round; do not return a second round for a defect this round could have found with the same evidence.

**Decision context.** Compare the package with the same confirmed decisions supplied to the author; report omissions, deviations, unresolved conflicts and nonexistent or unsupported references. Trace critical new cross-layer paths with evidence proportionate to risk; escalate what cannot be verified rather than treating it as established. Check the recorded baseline SHA and assess relevant drift, not drift alone.

**Verify claims by reading, not by running the suite.** Script checks establish only their stated properties; inspect their inputs and omissions where relevant rather than skipping those areas. R0 is a contract review: check each cited `path:line` against source and run at most one narrow command per changed package. Do not run the full test suite — it runs only at the sink and final acceptance.

**Bounded rounds.** At most two whole-package R0 rounds per change: the first review and one re-review of the revised package. Round 1 reports every blocker its evidence supports, in that one round. Round 2 checks the fixes against their findings and the interfaces, scenarios, task scopes and Verify they touch — not a fresh survey. When the second round still has blockers, say so plainly and stop; the human decides at CP-1 between accepting the recorded residual risk and directing a repair. After a directed repair the same reviewer may verify the fix diff only: that is a delta check against your own findings, not a third package round, and you still report any real defect it exposes. The brief states findings and the reviewed SHA; it must not tell you which verdict to return.

**Blocking has a definition.** A finding is a `BLOCKER` only with a falsifiable counterexample: a concrete input or state, the wrong outcome it produces, and why the current tasks and Verify cannot prevent it — a download that always 403s against a fixture seeded with the same value, or a fixture that passes while the real entry is unwired. Classify as `NIT` anything that changes only wording, numbering, anchors, or a future extension with no producer in this change. The main session records accepted NITs in `rulings.md`; they do not require a revision before CP-1. If your findings are all NITs, return the pass line — a second round exists for confirmed blockers, not for wording.

**Anchor drift is not a blocker.** A `path:line` that has moved but still points at the same symbol is a pure anchor-drift NIT: report it as `NIT` and keep reviewing the substance. Do not spend a round, and do not withhold the pass, because line numbers shifted — the author proofreads every `path:line` anchor once before FINAL. Raise `BLOCKER` only when the anchor no longer resolves to the claimed symbol, or when the drift hides a substantive change (the cited code no longer exists, or a different behavior now sits at that path).

**On PASS, return as the first line of your reply, exactly:**
```
R0: pass(<your-full-agent-uuid>@<reviewed-HEAD-sha-7-chars>)
```
followed by your findings summary (or "Findings: none."). Do not write `review.md` yourself: the main session records your line, so your read-only rule stays absolute. `freeze-check` voids the sign-off if the contract changes after it.

## FINAL — the one integrated review

Optional read-only input: `node "$PIPELINE_HOME"/r0-hotspots.mjs openspec/changes/<name> --final <reviewed-full-SHA>` (run in the repository) reads tasks.md from that exact commit and summarizes declared tasks, scenarios, risk surfaces, interfaces, scopes and dependencies from `tasks.md`, with SHA, source path, task line numbers, checked/Done state and parser errors. It requires that SHA to match the current `integration/<name>` tip; if the ref moved, stop and resolve the changed review target rather than using a different SHA. The local checkout and its uncommitted tasks are not used. Values follow the shared parser, including its `standard` default for missing Review. It executes no Verify and issues no verdict. It does not infer UI from paths; assess cross-task interactions, undeclared risks and semantic behavior manually, including for `mechanical` tasks. This summary is not a substitute for review of the approved contract and integrated diff.
This is the only code-quality gate in the pipeline. Every task was merged by a mechanical gate (Verify + scope + regression); none had a per-task reviewer. Read `main...<reviewed-full-SHA>` as a whole against the approved Spec and repository standards. The main session prepares the review workspace at that exact SHA; verify it and return the full SHA and verdict. After a blocker fix, review both the fix diff and the integrated result at the new final SHA; prior verdicts do not transfer to a different SHA.

- **Spec axis:** is every frozen SCEN actually implemented and exercised? Cross-task interactions, interface consistency, and whether the tests would catch the behaviour going wrong (not just "a test exists"). An assertion on production source text (`fs.readFileSync` + regex) does not prove runtime behavior — treat that claim as unproven.
- **Standards axis:** assess error handling, security, naming, duplication, and repository conventions as relevant to the change. Lint and typecheck do not replace standards review.
- **Match depth to what the diff actually changes.** Decide from the integrated diff, not from task labels or paths alone.
  - Rendered UI (components, styles, markup, client interaction): where the environment allows, exercise the real entry in a browser or the repository's UI test runner. Check states (loading, empty, error), keyboard and focus, accessibility, and responsive layout. Reading JSX alone does not show these. If you cannot run it, say so in Evidence.
  - Backend, persistence, concurrency, security or public interfaces: trace failure paths and boundaries, and check that tests would fail on a wrong implementation. Spend little on appearance.
  - A diff touching both gets both checks. Do not skip a part because its task was labelled `mechanical` or declared no risk.
- **Evidence:** report what was inspected or exercised, relevant risk and cross-task integration coverage, and any limitations. Do not infer safety from `mechanical` or missing risk labels.

Block only `SPEC_VIOLATION`, `CORRECTNESS_BUG`, `SECURITY_DEFECT`, `SCOPE_VIOLATION`; classify everything else as NIT. Report each blocker with `path:line` and the minimal fix. When the diff is large, work module by module and report all blockers in one verdict rather than stopping at the first.
