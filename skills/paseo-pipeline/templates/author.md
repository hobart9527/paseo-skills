# Change Author Brief

Mode: `FULL | REVISE`. Change: `<change>`. Output location: `openspec/changes/<change>/`.

## Shared contract
- Read `SKILL.md` (the normative rules; the `Entry and CP-1` section governs this stage); cite code claims as `path:line`. `LESSONS.md` is a 35KB historical evidence log, not a spec: consult a specific section only when a claim depends on past incidents, and never treat it as current procedure. Do not read `freeze-check`, parser or scheduler source to learn the rules: the schema templates and the structural check's own output are the feedback.
- Work in the assigned author workspace and change directory only. Do not create another workspace, recursively hand off, or reroute an already-assigned author task. If instructions conflict or the assigned workspace is unusable, stop and return `BLOCKED` with the conflict; do not improvise a route.
- Before writing, resolve and read every actual template referenced by `openspec-schema/schema.yaml` for artifacts this change needs. The schema's template list, not this brief's examples, defines the applicable templates.
- Run supplied read-only preflight before writing. Any required-command denial means stop: report exact command, cwd, denial, next action; do not retry through another tool, shell, or workspace. Preflight success does not authorize `freeze-check`; its denial is also `BLOCKED`.
- Do not edit business code. Return assumptions with a concrete verification method; mark unverifiable claims `UNVERIFIED`.
- Write only files under `openspec/changes/<change>/`. If a gate conflicts or blocks progress, return `BLOCKED` with the reason; never edit any other tracked file.
- Report changed files, evidence, unresolved decisions, and acceptance commands. Distinguish material contract choices needing human decision from ordinary assumptions; state options and consequences without deciding for the human. Identify authoritative inputs and their versions, including approved design and relevant ADRs, and flag any outside the contract commit. Do not invent provider/model requirements.
- One `gongbu` author writes the entire package. A human-approved design is optional; otherwise record assumptions from the request.
- Main-session brief must provide the absolute author workspace, baseline SHA, `PIPELINE_HOME`, and exact preflight and structural-check commands. Preserve that baseline in the report; reconcile Git state and evidence before R0.
- After the complete initial package first exists, immediately run the exact supplied structural-check command, before optional analysis or polishing. Fix structural blocks in place and rerun until it succeeds or a required command is denied. Report route separately from structural-check outcome: a `[ROUTE] handoff` is not a structural PASS. Never claim PASS without successful command output and exit code.
- Return `COMPLETE`, `BLOCKED`, or `INCOMPLETE`, plus workspace, baseline SHA, package commit SHA, structural command/outcome/exit code, blockers, and next responsible action. `COMPLETE` requires structural success against the committed package content; otherwise report `INCOMPLETE` or `BLOCKED` accurately.
- Before R0, main session reconciles the reported commit and evidence against the assigned workspace and Git state. Structural success alone does not authorize R0, CP-1, or execution; keep all existing R0 and human approval gates.

## Main-session brief fields
- Author workspace: absolute path; baseline SHA: full commit SHA.
- `PIPELINE_HOME`: resolved absolute path.
- Preflight: exact command to run before writing.
- Structural check: exact command to run immediately after the initial package is complete.
- Decisions, approved design (if any), and verified source references.
- **Project constants**: how Verify runs in a fresh worktree, test commands, and directory conventions the main session already knows. This replaces rediscovery; the author must not write `openspec/config.yaml`, which belongs to the target project.
- **Pending decisions (clarify)**: at most 5 items, each with a default, supplied by the main session before dispatch. Items with a default do not block; items without a default are asked of the human first.
- Human approvals and any known permission constraints; do not imply preflight authorizes later commands.
- Product decisions already settled, and the commit-bound path and version of every authoritative input, so the author discovers fewer of them mid-run. The main session sets a reconciliation point at the 30-minute mark and compares Paseo status with `git log` in the author workspace: no commit, or a newest commit older than ~10 minutes with the package incomplete, means one steer asking for a commit of the current state and a gap report. Having made a first commit does not clear the point.

## Denied command report
`BLOCKED` — command: `<exact command>`; cwd: `<absolute path>`; denial: `<verbatim denial>`; next responsible action: `<who must authorize or run it>`. Do not seek an alternate invocation to bypass the denial.

## Mode FULL — single author (`gongbu`, fast path)
- Input: the approved request, any human-approved design document, and repository context. Write the package directly to OpenSpec files and commit as each artifact lands (see Write-first budget). Do not return text for the main session to re-type.
- Main-session authorization must identify the target workspace, baseline, `PIPELINE_HOME`, and exact commands; do not infer them from another checkout or create a workspace.
- **The package is the OpenSpec native set, no more: `proposal.md`, `specs/<capability>/spec.md` deltas (SCEN-numbered scenarios), `tasks.md`, `acceptance.md`. Create `design.md` only when one of its criteria applies (cross-cutting change, new dependency/data model, security/performance/migration complexity, real ambiguity); otherwise skip it — task-local design is the worker's job. Never write a digest or a survey document; a code-reading conclusion lives beside the rule it supports, as `path:line` in the spec or decision it justifies.**
- Compile the approved design; do not re-solve it. When a design document exists, the package is its execution form: record conflicts with the current code, freeze the cross-task interfaces and constraints, slice the tasks, and map requirements to scenarios. Do not reopen the chosen technical route, re-narrate approved background, or write behaviour for which this change has no producer.
- Before tasks, write any cross-task Decisions in design, one line each naming owner and consumers; do not invent decisions or require a table. Derive tasks from behavior and those decisions. If two tasks touch the same file, or would each settle the same unfrozen decision, merge them, serialize with `Depends on`, or extract a `Kind: skeleton` with `Interface:` and consumer `Uses:`. After extraction, producer and consumer Write scopes must be disjoint; if still overlapping, serialize with `Depends on`. Tasks that only consume a decision already frozen in design may run concurrently. Never leave parallel tasks implementing the same decision independently.
- Before committing, check: do any two concurrent tasks share an unfrozen decision?
- **Read what your rules collide with, not the repository.** Before writing a rule, read the baseline it touches: the capability spec requirement it modifies (quote it verbatim under `## MODIFIED Requirements`), the enum/`CHECK`/migration it stores into, and the existing tests inside each task's Write scope. `rg` the identifiers the rule names. Do not survey capabilities no rule touches and do not fill alignment tables; a rule that contradicts a `CHECK` constraint, an existing scenario, or a passing test is a contract defect the author must fix now — review is for defects the author could not see.
- **Depth follows behavior and risk.** Assess actual data migration/persistence schema, credentials/security/audit, cross-task identity/idempotency, external protocol/vendor, and destructive/rollback risks. Freeze material semantics and verifiable outcomes in the applicable spec, design, or task contract; do not invent risks, internal-detail scenarios, or tables. Create design only when its criteria above apply.
- Give each task its required context and permissions. A shared contract may already be complete in the spec, design, or task packet; it need not be a file skeleton. Keep scenarios for observable behavior and semantics workers must preserve; assign `SCEN-*` ids and map them to tasks. Cite design sections only when a design exists.
- Acceptance records essential real-entry journeys, not a second list of unit tests or every spec scenario. Preserve required rows for delivery-critical behavior.
- Do not run the full test suite at authoring: it runs only at the sink and final acceptance (`SKILL.md` principle 5). Baseline reds: run one narrow command per changed package only when a task's Verify needs to know them.
- Run the exact structural-check command supplied in the main-session brief as soon as the initial package exists. R0 sign-off does not exist yet. Report its command, outcome, exit code, route, waves, max width, and critical path separately. A route of `handoff` is not a check PASS. Read its `CRITICAL` line: each `-logical->` edge is yours to justify or drop (contract-first); each `-scope->` edge is forced by a shared file. Fix blocks in place and rerun; if permission is denied, use the denied-command report and stop.

## Authoring order
| Step | Artifact | Then |
| --- | --- | --- |
| 1 | `proposal.md` (+ `## Baseline`) | commit |
| 2 | `specs/` — freezes the SCEN id set | commit |
| 3 | `design.md`, only if its criteria apply | commit |
| 4 | `tasks.md`, then `acceptance.md` | commit each |
| 5 | structural check on the complete package | fix, rerun |

Before step 2 assigns ids, run one `rg` over scenario headings in baseline `openspec/specs/**` and other changes' `openspec/changes/*/specs/**`, choose ids outside that set, then commit as the frozen set.

Each step: write, commit with done/remaining in the message, and run `openspec validate`/`openspec status` as a mid-run check when available. No staged freeze-check exists; the first structural check runs when the package is complete, and failures are fixed and rerun until it succeeds or a required command is denied.

## Write-first budget
Measured failure: two authors spent ~55 min each on analysis and wrote no file, because the plan lived only in thinking and was re-derived every turn. Context compaction then discarded it. The budget below is an experiment target, not a guarantee; it never lowers a gate.
- **Clock.** Run `date` first and record the start. Check it at each commit. Anchors: first files committed by minute 10 (`proposal.md`, spec skeletons with the decisions you already hold); complete package plus the structural check by minute 20; stop at minute 25. Measured pace was about three tool calls per minute, so roughly 30 / 60 / 75 calls approximate the same anchors when no clock is at hand.
- **Write, then verify.** Once you judge context sufficient for a rule, write it. Every later lookup must serve the rule being written, not reopen the plan. The plan lives in the files.
- **Commit each artifact as it lands.** Put done and remaining items in the commit message so `git log` reconstructs progress after a context compaction; a summary is not state.
- **Bounded collision checks.** Exactly four: the Requirement text you modify (quote it verbatim), the storage constraint it writes into (`CHECK`/enum/migration), existing tests inside each task's Write scope, and how each Verify runs in a fresh worktree. The last is answered by the brief's Project constants when supplied; check it yourself only when they are absent or a task's Verify falls outside them. Read baseline files with `rg -n` and line windows; never read a multi-thousand-line file whole. If one output exceeds ~20k characters, narrow the query.
- **Open decisions are recorded, not resolved.** A material product choice the inputs do not settle goes in `proposal.md` as `OPEN-DECISION`: options, consequences, a recommended default. Continue on the default. Return `BLOCKED` only if the choice changes the task graph or ownership. Never decide for the human or invent behavior to close it.
- **Dependencies.** If preflight reports `MISSING_DEPENDENCIES`, record that each affected Verify cannot run until the main session resolves it; a zero exit status is not readiness.
- **At the stop point**, commit what exists and return `INCOMPLETE` with the gap list. Do not extend the budget on your own. Budget exhaustion is never a `COMPLETE`, and `COMPLETE` still requires the structural check to succeed on committed content.

## Mode REVISE — bounded repair after R0

Same author, same workspace. The brief carries the review round, the reviewed SHA, and the confirmed BLOCKER list with the human's rulings. This is a repair, not a second authoring pass.
- Fix the named findings at their cited locations. Then update exactly what those fixes change: the interface or constraint they touch, the SCENs and acceptance rows, the owning task's Write scope and Verify. Leave the rest of the package byte-identical unless the fix proves it wrong.
- Do not regenerate the package, re-derive the DAG, or restyle untouched documents. A whole-package rewrite is the documented way repairs introduce new blockers.
- Do not fix recorded NITs in this pass. If one turns out to change behaviour, persistence/security semantics, or whether a Verify can trust its result, say so and treat it as a blocker rather than slipping it in.
- After editing, re-run `freeze-check --structural` and the narrow checks the findings cite. Commit as a new commit; the reviewed SHA moves, so never reuse the old sign-off line.
- Return one block per finding — `finding ID`, location changed, SCENs/tasks/Verify touched, evidence, and anything deliberately not changed — plus new commits and the freeze result. `rulings.md` already has the record; do not add a second report file.

## Task design

Optional read-only aid: `node "$PIPELINE_HOME"/r0-hotspots.mjs openspec/changes/<name>` lists declared task Uses, interfaces, risk surfaces and Verify plus MODIFIED/REMOVED requirement headings from the local worktree draft, not a commit-bound source. It never executes Verify. It uses the tasks parser and only recognizes standard spec headings; missing declarations, other formats, call sites and semantic effects are not discovered. Parse errors and missing/unreadable specs require attention. This is not validation or a substitute for independent R0 or CP-1.
- Split into vertical behavior slices: behavior + wiring + affected fixtures + tests together. No fixture-only or wiring-only task. Wave 0 only for a real shared contract and only actual consumers depend on it.
- Each task has disjoint Write scope, explicit dependencies, claimed SCENs, and a narrow executable Verify inside its scope. Reserve full suite for one sink and final acceptance. Name Verify so it can run in a fresh worktree: prefer a command whose runner is a repo dependency or lockfile-pinned, since a global-only runner (`tsx`, `vitest` installed elsewhere) fails there.
- **Concurrent tasks must have fully disjoint Write scopes, including test paths.** `freeze-check` rejects scope overlap between tasks that can run in parallel. Never list a shared parent directory (e.g. `test`) when two concurrent tasks each own a file under it — list the individual files or subdirectories instead (e.g. `test/add.test.mjs` and `test/mul.test.mjs`). A coarse `test` scope on two parallel tasks collapses concurrency to zero.
- **Contract-first edges preserve real concurrency.** When concurrent cross-layer or cross-module tasks need a stable shared interface before producer implementation completes, freeze its shape and required semantics once in a worker-reachable authoritative contract. Use a Wave 0 skeleton with `Interface:`/`Uses:` when it is the smallest executable contract, or an existing design/task contract when it is already authoritative and reachable. Do not create a skeleton solely for an internal signature with no concurrent consumer.
- **Use DAG edges for actual dependencies.** For an executable skeleton, mark the owner `Kind: skeleton` + `Review: mechanical`, declare the provided path/symbol with `Interface:`, and connect the owner to each consumer's actual dispatch dependencies; `Uses:` waits for skeleton ancestors at dispatch and target Done at merge. Overlapping Write scopes still need `Depends on`. Use `Depends on` when a consumer's final Verify needs another task's behavior or file; merge replay cannot rescue a worker unable to deliver. The first Verify may be red. `Reads:` is read-only and does not establish existence or readiness; an existing baseline file, a file the task itself creates, or an optional regression read needs no invented edge. Scope only permits ownership, not proof of content or a commit. Keep concurrent tasks' Write scopes disjoint; do not serialize independent work or invent edges.
- **Scheduling weight and risk metadata.** `Est: S|M|L` (default M) feeds the weighted critical-path model. `Review:` no longer selects a process: every task is executed by one worker and judged by the one FINAL integrated review, so there is no inline per-task review to defer. As author guidance, mark material `persistence`/`security` risk `strict` for FINAL attention; freeze-check does not require this for every task or validate risk label completeness. A missing risk label does not establish safety. `deferred` is a legacy label, not an unrestricted alias: freeze-check rejects it on sinks and tasks declaring those risk surfaces. `mechanical` does not exempt a task from semantic review.
- **Split shared files, don't chain them.** Several tasks writing one file (e.g. a service) are forced serial by `SCOPE_CONFLICT`. Where the design allows, split that file by feature so each task owns its own; if it cannot be split, accept the chain and say so.
- When runtime behavior is claimed, Verify must execute the code under test. A test that only reads production source (`fs.readFileSync` + regex/string match) cannot prove runtime behavior, regardless of `Review` label: load and run (or render) code when behavior is claimed. Source-text assertions may verify textual properties only; R0 checks whether each Verify can falsify its claimed outcome.
- **Self-check each SCEN against its owning task before committing tasks.md, and fix the task, not the check.** Entry owned: the entry point named for the SCEN in acceptance.md (where the outcome is observed, e.g. the submit handler) is inside the owning task's Write scope, or the owner `Depends on` the task that owns it; a component or unit test beside the entry does not stand in for it. Verify can fail: the owner's Verify runs a test that exercises that entry or function and would fail before the change, and the test file is in the owner's Write scope (or created by it); an existing test that already passes and never calls the code under change cannot carry the SCEN. Names exist: confirm each field, symbol or route a task or design names once with `rg` in the tree (or in a file the task creates); design.md names decisions (`D-01`) and affected modules only, never task ids; tasks declare `Implements:` decision ids, and every id must exist in design.md.
- Do not pad DAG to qualify. If real `maxWidth < 2` or task count < 4, recommend Tier 2.

## Decision Context

Use confirmed decisions supplied in the brief and verify cited references exist. Record decision coverage and unresolved conflicts in existing artifacts or the return envelope; do not invent an ADR or present assumptions as approved decisions. Trace a new cross-layer path end to end only where it touches persistence, security, an external boundary or a shared semantic, and stop once the evidence supports the rule; explicitly escalate unverified claims or conflicts as `UNVERIFIED` or `OPEN-DECISION` instead of widening the search. Preserve the actual baseline SHA and assess relevant drift before relying on its evidence. Never fabricate scope or DAG edges to satisfy a checker; capture a minimal reproduction and escalate when reasonable investigation cannot resolve a suspected false positive.

## Return envelope
`status` (`COMPLETE` / `BLOCKED` / `INCOMPLETE`), `mode`, absolute workspace, baseline SHA, package commit SHA, changed paths, evidence, decision coverage, unresolved conflicts, assumptions/unverified, task count, max width, route, exact structural-check command/outcome/exit code, blockers, and next responsible action. `COMPLETE` only when the structural check succeeded on committed package content. If blocked by permission denial, include exact command, cwd, verbatim denial, and who must authorize/run it; do not claim route as check success. In `REVISE` mode add: one block per finding (ID, location, affected SCENs/tasks/Verify, evidence, not changed), new commits, and the new reviewed SHA.
